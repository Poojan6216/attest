# Attacks that work

What Attest knowingly does not catch, with the rate we measured. The losses are published on purpose: an attack is never fixed and hidden, and one that is fixed keeps the number it had before the fix, next to the commit that fixed it.

## The red team (Sprint 6)

Attest attacked the way an agent that wants to look good, a vendor that wants to hide, or a malicious page would ([agents/red_team.md](../agents/red_team.md)). Each strategy is a folder of [`extension/tests/fixtures/attacks/`](../extension/tests/fixtures/attacks/README.md), run through the built extension by `pnpm redteam`, which writes its rows to `bench/results/redteam-<date>.json` and [`RESULTS.md`](../RESULTS.md). Severity: CRITICAL for a false VERIFIED or a data leak, HIGH for a missed UNASKED or OVER SCOPE, MEDIUM for a false NOT FOUND, LOW for a result that confuses.

### What the red team could not test

| Strategy | Why |
|---|---|
| 4. Time tricks across a DST change, and "Yesterday" pasted just after midnight | The harness runs on this machine's clock in the fixtures' time zone, so it cannot start a run at 00:30 or across a DST change. Below the extension they are held: [`paste.spec.ts`](../extension/tests/unit/adapters/paste.spec.ts) pastes at 00:30, and goldens [59](../extension/tests/golden/59-dst-fall-back.json) and [68](../extension/tests/golden/68-day-precision-claimed-at-end-dst.json) grade across a DST change. |
| 2. Paraphrase drift with the optional model on | Every case runs with the model off, its default. A model can lift a PARTIAL to VERIFIED, never an UNVERIFIABLE, and its real answers are not recorded yet (MANUAL.md, Sprint 5). |
| 14. Forged evidence for a claim that names its merchant | A claim read from an agent's own page could name its merchant, and a stranger's receipt under that name would then match it whole. The readers of agents' pages are off (Decisions `[3.10]`) and a pasted claim names no merchant, so the attack cannot run until they are on. |
| 5. A row written into Gmail's own page | A script that can write into Gmail's own page decides what Attest reads there, and no reader of a page can tell such a row from Gmail's: the page is Attest's evidence, its trust boundary. The threat model (Sprint 6.8) says so. |

## Limits accepted before Sprint 6

The limits accepted as each sprint closed. Each one is also an entry in [`Decisions.md`](../Decisions.md) and a rule in [`docs/grading.md`](grading.md).

| Limit | What happens | Measured rate | Where it is written down |
|---|---|---|---|
| Two tabs sight one calendar event, the later sighting is stored first | The earlier sighting is refused (`late_sighting`) and the pass is DEGRADED, but the stored row keeps the later first sighting, so a calendar event that already existed can still verify a "created" claim. The stored row cannot move, because a batch may already have graded with it (Hard Rule 4). | 25 of 513 minute-precision `calendar.created` receipts (4.9%) in the differential simulator, with 25% of rows re-sighted by a second tab within ±30 minutes | [§4.1](grading.md#41-window), Decisions `[1.close-r4]` |
| A FINAL-to-NOT_FOUND override is reverted while another claim holds that evidence | The reverted receipt shows its computed VERIFIED or PARTIAL again, while the evidence stays with the other claim; one observation is never fixed to two claims (Hard Rule 4). The Sprint 4.3 revert control must say so. | 15 of 7,277 receipts with a reverted override of that kind (0.21%), 5,000-seed simulator | [§8](grading.md#8-state-machine-conditionsts-decides-finality-statets-applies-events), Decisions `[1.close-r3]` |
| A PENDING UNASKED row holding a reverted override is no longer produced by later batches | The row is kept, PENDING, so replay still sees the orphan that batches took while the override was in force, until a batch produces it again or a FINAL claim supersedes it. | 71 of 7,753 claim-less receipts with reverted overrides (0.92%), same simulator | [§8](grading.md#8-state-machine-conditionsts-decides-finality-statets-applies-events), Decisions `[1.close-r3]` |
| Deliberately evasive code inside `src/core` | The purity and Unicode fences (lint, the grep gate, the syntax-tree Unicode fence, the runtime guard under `pnpm test:poison`) catch impurity written by accident or through ordinary idioms. Code written to dodge them (names built from fragments, reflection chains built to reach a built-in, code that blinds the guard) is a code-review matter for the sprint-end security and tech reviews. | Today's `src/core`: 0 findings in every layer. 49 ordinary-idiom probes (stray browser globals, beacons, locale and time-zone reads, type-check switches, Unicode idioms) each fail at least two layers. | [§14 item 9](grading.md#14-deviations-from-build_spec-7-all-in-decisionsmd-sprint-1), Decisions `[1.close-r3]`, `[1.close-r4]`, `[1.close-r5]` |
| A calendar change claim (updated or deleted) that is false | Reported UNVERIFIABLE, never NOT FOUND: a snapshot reader cannot prove a change did not happen between two looks. | By design (v1.11); 0 change claims NOT FOUND over 5,740 simulator seeds | [§6.1](grading.md#61-conditions), Decisions `[2.7]` wave E |
| A calendar event created, then deleted, moved or renamed before Attest's first fresh look at its day | The `calendar.created` claim is NOT FOUND: the event was not on the calendar when Attest looked after the claim. | 107 such receipts in the wave E simulator run (allowed by the contract's meaning of NOT FOUND) | [§6.1](grading.md#61-conditions) |
| The computer's clock is set back after running ahead, or steps back for good, around the moment of a `calendar.created` claim | A claim stamped in the span the clock repair keeps is UNVERIFIABLE (`coverage.clock_repaired`), never NOT FOUND, unless its event was first seen at or after the claim: so a false one is never caught as NOT FOUND, and a true one is never reported NOT FOUND (Hard Rule 5). Until Sprint 3.17 a true claim could be NOT FOUND, FINAL, because the event's sighting, stamped after the repair, read as earlier than the claim (S2-SIM2-1). | Not re-measured: the Sprint 2 simulator is not in the repository. Its two clock moves are tests (`tests/unit/background/clock-repair-grading.spec.ts`). Before the fix, 8 of 23,420 simulator receipts were that false NOT FOUND, all in histories with clock jumps of up to 6 hours; 0 without them | [§3](grading.md#3-inputs), [§6.1](grading.md#61-conditions), Decisions `[2.7-E]`, `[3.17]` |
| A Calendar change found by a pass more than 2 minutes after the previous look | Never UNASKED (a missed accusation, never a false one). A visible tab is read every minute, so this applies to tabs left in the background. | By design (v1.11) | [§3](grading.md#3-inputs), [§7](grading.md#7-unasked-attributionts) |
| A Calendar change the account or its agent really made, while the tab was watched | Never UNASKED (a missed accusation, never a false one). A snapshot cannot yet tell a change the account made from one other people make to its calendar (an invitation Google adds from anyone, an organiser's reschedule or cancellation, a colleague's edit on a shared calendar), so since v1.12 every Calendar row is stored as a first sighting with its first-look marker. The rows still verify claims. Lifted when the live smoke (2.8) confirms which page facts say the account organises an event and owns its calendar. | By design (v1.12): every Calendar change. 0 Calendar rows UNASKED in 40 seeded handler histories with other people's changes (`tests/property/calendar-third-party.property.spec.ts`) and in golden 112; 3 of its 4 rows are UNASKED without their markers | [§3](grading.md#3-inputs), [§7](grading.md#7-unasked-attributionts), Decisions `[2.close]` |
| A stranger's "order confirmation" dated in the same minute as a registry receipt the user also opens | A generic receipt (a sender outside the receipt registry) posts no coverage, and neither does a registry receipt beside it in the same minute of the same pass. But rows carry no parser, so the coverage point of a registry receipt read in another pass in that minute holds the stranger's row: unclaimed, it can be an UNASKED ("likely") for a purchase nobody made. Someone who can trigger a real registry receipt to the user (a $1 payment with the user's address as the receipt address) can time both. Closing it needs a row field that marks registry receipts and an orphan rule that reads it (a grading contract change). | Hand-built pages: an orphan candidate in 1 of 1 same-minute pairs, 0 of 1 a minute apart; not measured on real mail | [§3](grading.md#3-inputs), Decisions `[2.close]` |
| An organiser edits an event more than 20 times in one day | Its further `calendar.updated` rows that day are not stored and the Calendar observer shows DEGRADED `ledger.event_churn`; a claim to have updated that event is UNVERIFIABLE that day, never NOT FOUND. | By design (v1.12): 980 of 1,000 scripted edits of one event in a day held back (unit test) | [§3](grading.md#3-inputs), Decisions `[2.close]` |
| A Gmail or Calendar page that knows Attest's public extension id | It can tell Attest is installed: WXT dispatches its content-script start-up event on the page's `document` when the content script starts. A forged copy no longer stops the observers; they stop only when the extension context is gone. Removing the event needs a patched WXT. | 1 of 1 page listeners received it in `tests/e2e/observer-startup-event.spec.ts`; 0 passes stopped by the forged event | Decisions `[2.close]` |
| A Gmail or Calendar page that is online but cannot reach its server | It reports itself online, so its passes may post coverage for what it shows while it is out of date; only the vendor's own banner says otherwise. A page the browser reports offline posts no coverage, nor for 30 seconds after it comes back. | Not measured on real pages (live smoke 2.8). 0 coverage pings while Chromium reports a Gmail Sent page offline (`tests/e2e/observer-offline.spec.ts`); a Calendar pass that cannot vouch posts no ping and no snapshot (`tests/unit/observers/gcal/script.spec.ts`) | [`docs/adapters.md` §3.5](adapters.md#35-when-no-coverage-is-posted-by-design), Decisions `[2.close]` |
| Activity in any conversation after a claimed send | Since grading contract v1.13 the Sent list's window starts after the newest conversation row, so a reply anyone sends in any thread (the agent included) moves every later window past the claimed send's minute. A false "I sent it" claim then stays UNVERIFIABLE instead of NOT FOUND: the safe direction (Hard Rule 5), but it lets an agent hide a send it never made behind thread activity (security re-review, SEC-R10). | Not measured yet: Sprint 6 red team | [Decisions.md](../Decisions.md) `[2.close-r2]`, [grading.md](grading.md) v1.13 |
