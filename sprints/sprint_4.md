  - Carry-forward from the Sprint 1 close (docs/grading.md §3 Background obligations): stamp the override's `at` inside the readwrite transaction that writes it, so replay applies it exactly where the batches did (an override is in force only in batches graded strictly after its `at`).
  - Carry-forward from the Sprint 1 close (docs/grading.md §4.3, §7, §8; Hard Rules 4, 6): undo an override with `transition(receipt, { event: 'revert', at })`, stamping `at` inside the readwrite transaction that writes the reverted receipt, as for an override's `at`. The receipt keeps the override in `reverted`: never drop or edit that list. When an override from FINAL to NOT_FOUND is reverted while another claim's receipt holds the same evidence, the evidence stays with that claim and both receipts name one observation: the revert control must say the evidence now belongs to another claim, or refuse that revert. A PENDING claim-less (UNASKED) receipt that holds reverted overrides can stay PENDING after the last batch that produced it; the popup and side panel must not show it as "checking" forever. Done-when also covers: an override reverted after a batch ran replays with 0 mismatches.
  - Carry-forward from the Sprint 1 close (SIM-1, R4-EVENT-ORDER; docs/grading.md §3 Background obligations, §8; Hard Rule 4): write every override and every revert through `writeUserEvent(db, write, { notBefore: lastEventAt(receipt) })` (src/ledger/repo.ts). In one readwrite transaction over `receipts` and `meta`, read the receipt, then call `writeUserEvent` inside it with `notBefore` = `lastEventAt` of that receipt, and in `write` apply `transition(receipt, { event: 'override', grade, reason, at })` or `transition(receipt, { event: 'revert', at })` with the `at` it passes, and store the result. Never stamp an event with `nowIso()` yourself: after a batch, a clock that went back would put the event in force for a batch that never read it, replay would fail, and after a revert every later batch could throw `fixed_conflict`. `writeUserEvent` stamps the latest of now, the last batch instant + 1 ms and `notBefore` + 1 ms, so a revert or an override whose clock went back below the receipt's own last override or revert is saved 1 ms after it instead of refused. Await only ledger operations inside `write`. If `transition` refuses the event (the receipt is not in a state the event applies to, e.g. already overridden), show that the change was not saved and write nothing. The detail drawer shows an observation's `sightedAt` as when it was first seen and `observedAt` as when it was stored. Done-when also covers: with the clock 5 min 1 s back after a batch, an override and a revert are stamped 1 ms after that batch; with the clock back below the receipt's own last override (or revert), the revert (or override) is stamped 1 ms after it and saved; in both, replay reports 0 mismatches and the next batch runs (tests/unit/ledger/user-event.spec.ts is the model).
